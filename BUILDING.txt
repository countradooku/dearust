Cargo build and migration boundaries
===================================

Requirements for this Rust workspace
------------------------------------
Rust 1.85 or later, Cargo, and a host linker are required. Native object staging
also requires llvm-objcopy; integration checks use cc, ar, nm and readelf. `cargo xtask check`
also requires the rustfmt and Clippy toolchain components. There are no
third-party Rust dependencies, build scripts, CMake calls, network downloads,
or generated-code prerequisites in the migrated workspace. Optional differential
and linked-artifact checks require the pinned references and named native tools.

Run commands from this checkout, or a directory inside it:

    cargo xtask build
    cargo xtask check
    cargo xtask test
    cargo xtask bench
    cargo xtask install --destdir /path/to/stage
    cargo xtask help

`build` builds all migrated workspace packages except xtask with release
optimizations, then rebuilds the native libsimple static library without std
and with panic=abort. This final C-linked archive does not contain a Rust
allocator or unwinder; libc supplies syscall and abort.
The tools are placed in target/release (or CARGO_TARGET_DIR when configured).
`check` stops at the first failure: rustfmt --check, Clippy for every workspace
target with warnings denied, then workspace tests including doctests.
`test` runs workspace tests and doctests. It leaves optional upstream
differential suites ignored; the tests describe the reference-tool environment
variables for running them explicitly.
`bench` runs only the metadata benchmark in release mode. Its figures measure
the Rust parser on synthetic fixtures; they are not evidence of a speedup
over upstream or the performance of an entire Darling installation.

All xtask Cargo dependency-resolution commands use --offline --locked.
No task installs software, changes system paths, invokes a shell, or builds
the upstream CMake tree. An unavailable tool or failing child process makes
the task fail; a nonzero child exit code is forwarded when representable.

Ordinary Cargo commands also work without xtask:

    cargo build --offline --locked --release --package dearust
    cargo test --offline --locked --workspace

This workspace currently migrates selected host utilities. It is not yet a
complete Darling runtime. Its three Rust runtime slices have launched selected
macOS command-line programs inside an existing locally modified installation. Cargo is the
primary build system for the migrated Rust code; the existence of this
workspace does not replace the remaining upstream build graph.

Functioning executables: elfdep, getuuid, bsdln, print_wrapped_elf,
darling-coredump and wrapgen (partial loader-name resolution; see README.txt). No libbsd
dependency is needed for the Rust bsdln. Mach-O metadata supports 32/64-bit thin
and fat containers in either byte order, including FAT64. UUID text and ELF
dependency stdout/exit semantics match the supported valid upstream fixtures.
Malformed inputs fail before output. This intentionally rejects corrupt files
which the C readers may accept or read out of bounds. bsdln also refuses a
forced hard link onto the same inode, preserving a source upstream can delete.

The CLI readers currently copy file contents with std::fs::read, while the old
C tools use mmap. This avoids an unsafe mapping boundary and concurrent-file
mapping faults, but can increase memory use and I/O for large inputs. No general
performance improvement over upstream has been established. Parser benchmarks
exclude file reading, command startup, and the rest of Darling.

Cargo host artifact staging
---------------------------

`cargo xtask install --destdir PATH` builds declared host binaries with an
explicit Linux host target and stages the graph in xtask/host-artifacts.tsv.
Build-only tools retain their original build-tree executable paths; the core
converter uses its upstream bin/darling-coredump install rule. See
xtask/README.md for publication semantics and filesystem regression coverage.
The typed graph also stages libsimple at the upstream Linux static archive
path. Its C-link integration harness checks the staged archive. The manifest
is deterministic. It also stages a native no_std errno ELF object at
lib/darling/native/dearust_errno.o. This stages six tools, a native library and
a native validation object, not the complete runtime or required Darwin objects.

Legacy integration (optional)
-----------------------------
integration/CMakeLists.txt and integration/bsdln.CMakeLists.txt are transitional
adapters for the original THREE-tool slice within the remaining upstream graph. They invoke Cargo for these tools,
preserve the executable paths consumed by upstream installation rules, and do
not affect native Cargo builds. Their presence is not a CMake replacement for
the full project. See upstream-rust-tools.patch and README.txt for application
instructions and the pinned reference revision.

What the remaining CMake graph does
----------------------------------
Inspection baseline: darlinghq/darling commit
60ba801decee7a00782f74f6be4c8ffb013f79ff.

The upstream root CMakeLists.txt configures Clang, C/C++, assembly, component
selection, architecture slices, dependency discovery and installation.
src/CMakeLists.txt first builds Linux host tools and darlingserver, then
switches to Apple target triples, SDK headers and Darwin compiler definitions
for the emulated system libraries. It includes external subprojects for
dyld, the Objective-C runtime, libc, libpthread, frameworks and other tools.

cmake/darling_lib.cmake selects ld64, Darwin install names and dylib versions,
orders multi-pass linking for mutually dependent libraries, and arranges
lipo architecture slices and debug symbols. cmake/mig.cmake generates Mach
IPC client/server C sources and headers, including architecture-specific
variants and xtrace output. Installation rules arrange the Darling prefix
and symlinks; the root build also discovers Setcap.

Cargo's ordinary package dependency graph does not reproduce these target
ABI, code-generation, circular-linking and filesystem-install semantics.
A full replacement needs explicit equivalents and compatibility tests for
each of them, plus Rust ports or deliberate legacy adapters for the foreign
language subprojects. A CMake invocation hidden inside build.rs would still
depend on CMake and would not constitute that replacement.

Migration path
--------------
1. Keep independent host tools as Cargo binary targets with behavioral and
   malformed-input regression tests. This is the current implementation.
2. Add typed, independently tested generators for MIG, SDK metadata and other
   generated artifacts, with deterministic inputs and declared outputs.
3. Define separate host and Darwin-target packages, and validate their ABI,
   exported symbols, loader behavior and architecture coverage. Introduce
   narrowly reviewed unsafe only at required OS/ABI boundaries.
4. Implement the required linking, slice assembly and installation steps as
   explicit xtask operations, testing actual artifacts against upstream.
5. Retire each remaining CMake target only after the corresponding Rust
   component and compatibility tests exist. The legacy CMake build remains
   required to build unported upstream components during that process.

These are remaining engineering requirements, not implemented task commands.

Native synchronization ABI check
--------------------------------

  crates/dearust-libsimple/scripts/check-abi.sh /path/to/upstream \
    target/release/libdearust_simple.a /path/to/reference-output

Requires cc, nm, timeout and POSIX shell in addition to the Cargo build. It
compiles committed original headers/source and the same bounded C pthread
harness against upstream and Rust independently. All 14 external symbols,
state layout, lock/CAS/once/RW/condvar concurrency and publication are checked.
The state-machine core forbids unsafe; SAFETY.txt inventories the narrow
native FFI/futex boundary. Native Linux and Darling x86_64 backends are supported; i386/other architectures
and clean pinned-runtime startup remain pending. Native C
consumers of the staged no_std archive link with -pthread only. This does not
replace libSystem initialization.

Pinned errno runtime slice
-------------------------
`cargo xtask build` builds dearust-errno as an always-no_std rlib. `install`
also invokes Cargo rustc in an isolated fresh output directory to emit one native
PIC object with LTO disabled. llvm-objcopy preserves global linkage while setting
the two original C symbols to hidden visibility. No panic handler, allocator,
OS shim or unresolved symbol is bundled into this object. It can link beside
libsimple's final C-linked no_std archive. The remaining emulation CMake targets
require Darwin Mach-O/fat objects; this ELF object does not replace those targets.

Verify committed original sources/headers and reproduce the signed overflow:

    python3 tools/check_errno.py --upstream /path/to/darling \
      --xnu /path/to/exact-pin/xnu --object /path/to/stage/lib/darling/native/dearust_errno.o

Add --benchmark --report /path/to/record.json for 21 alternating synthetic call
measurements after warmup. This optional check needs clang, UBSan, nm and readelf.
All source/header blobs come from the documented Git pins, not working files or
host errno constants. It compares 131,073 range inputs and one million random
inputs, then independently verifies Rust's defined INT_MIN result and C's UBSan
failure. It verifies both original globals and empty undefined-symbol output.

Darling x86_64 runtime objects and actual consumers
-------------------------------------------------
Requires the x86_64-apple-darwin Rust target and LLVM ar/nm tools. It does not
require an Apple SDK or a target linker just to emit the Rust runtime objects:

    cargo xtask runtime --target x86_64-apple-darwin --destdir /path/to/darwin
    cargo xtask runtime --target x86_64-unknown-linux-gnu --destdir /path/to/native
    cargo test -p xtask --test runtime --offline --locked -- --ignored

The runtime graph in xtask/runtime-artifacts.tsv declares libsimple's Darling
backend, both futex adapters, errno conversion and the thin libsimple archive.
Every object disables std, LTO and final panic ownership. Mach-O errno globals
retain private-extern visibility; the futex and 14 lock C exports match upstream.
The native runtime command uses the Darling ABI too, not libsimple's libc shim.

Execute the real pinned guarded table/close sources with both C and Rust chains
using tools/check_darwin_runtime.py as documented in tools/DARWIN-RUNTIME.txt.
The host TLS cerror/abort adapters are explicitly test-only. Actual Darwin TLS,
cancellation and bootstrap behavior are not inferred from that native execution.

The pinned original targets can be built without source edits:

    cmake --build /path/to/original-build --target emulation system_kernel -j4

Then use its complete final link inputs with the Rust replacements:

    python3 tools/relink_system_kernel.py --build /path/to/original-build \
      --runtime /path/to/darwin --output /path/to/absent-output \
      --report /path/to/report.json

This legacy integration command reads the already-built tree and executes the
original production link argv directly. It replaces exactly the x86_64 errno,
futex and libsimple slices, adds no stubs/relaxed symbol resolution, writes to a
fresh directory outside the original build, checks public definitions/imports,
and preserves the original i386 final dylib slice unchanged. The linker map proves
that real guarded/close code calls the Rust chain and original cerror/raw syscall/
bootstrap abort. This is not a Cargo replacement for unported original inputs.
system-kernel-integration.json records this pinned-baseline link gate; installed
runtime execution is a separate check described below.


Installed-runtime application checks
------------------------------------
Actual x86_64 execution uses the locally modified source/build at
/home/radud/darling-lol/build/darling-src. Its existing server and kernel build
artifacts match the installed binaries byte-for-byte. Relinking the same original
objects with the three staged Rust slices preserves 1,370 public definitions and
40 imports. A matching original relink serves as the comparison. Both variants
boot in separate exclusively owned prefixes, leaving installed files unchanged.

The execution checks cover Bash pipelines, SQLite create/insert/aggregate, Python
JSON/SHA-256, offline curl version output, Objective-C, pthread/TLS, fork and Mach
semaphores. The running launchd process maps the copied Rust dylib's inode; its
SHA-256 is recorded. This verifies actual loading and execution of the mixed
runtime, while most runtime implementation remains original C/assembly.

Do not inject the clean pinned kernel into this installed server: two locally
added fileport RPC calls shift the protocol numbering. That mismatch prevents
boot in both the original pinned and Rust pinned variants. The pinned link script
above also preserves an i386 slice, whereas the installed build is x86_64 only.
Broader GUI compatibility, cancellation semantics and clean pinned full-runtime
boot need separate validation. Selected executed GUI checks are documented in
GUI-VERIFICATION.txt. App smoke checks do not retire any original build target.

mac-app-verification.json records 29 checks per matching variant: 24 strict
expected-output passes and five shared mismatches. The latter are two lockset
assertions, a CFURL fixture requiring absent /home, unsupported/failing libproc
queries, and an extra timestamped cfbridge NSLog line despite a zero exit.
No status/exit regression was observed between the matching variants in this suite.
The record includes hashes and paths to raw execution and mapping evidence.
